01 Why a resolver

There is no schema catalog anywhere in sqlrunner. When a SELECT reads b.id, nothing on disk says what table id ultimately comes from — that has to be worked out purely from the SQL text.

The trick is direction. Instead of expanding * forward (which requires knowing a table's real columns), the Resolver walks backward: a relation asks its own FROM/JOIN sources “do you have a column named X?”, and that question recurses until it hits an external table, which is treated as terminal and trusted at face value.

Every arrow above is one recursive resolver.resolve() call. This exact chain is traced live in §8.

One structural rule makes this tractable: facts stop at derived columns. resolve() returns the derived node itself (e.g. rn, a ROW_NUMBER()) rather than reaching into its inputs — so evidence gathered about sum(x) can never leak backward onto x. See _resolve, lineage.py:164–167.

02 Resolution, the return type

Every resolver method funnels into one small dataclass.

# lineage.py:74-91
@dataclass
class Resolution:
    nodes: list[ColumnNode] = field(default_factory=list)
    confidence: Confidence = "explicit"
    status: ResolutionStatus = "resolved"   # resolved | ambiguous | unresolved

    @property
    def resolved(self) -> bool:
        return self.status == "resolved" and bool(self.nodes)

    @property
    def origins(self) -> list[ColumnOrigin]:
        return [ColumnOrigin(node=node, confidence=self.confidence) for node in self.nodes]

nodes is a list, not a single value, because a resolution can legitimately fan out — a UNION branch column has one origin per branch (_resolve_branches, lineage.py:218). confidence is the weakest link across the whole chain: every hop takes weakest(current, upstream) (lineage.py:70–71), so one shaky guess anywhere downgrades everything built on top of it.

03 Two entry points

resolve_column_expr is for a column as it's actually written (with sqlglot's exp.Column node, so it still has a .table alias attached). resolve is the lower-level, alias-free primitive that everything — including resolve_column_expr — bottoms out in.

# lineage.py:124-135
def resolve_column_expr(self, info: RelationInfo, column: exp.Column) -> Resolution:
    bound = self.bind_alias(info, column.table or None, column.name, column)
    if bound is None:
        return UNRESOLVED
    ref, confidence = bound
    result = self.resolve(ref, column.name)
    return Resolution(result.nodes, weakest(confidence, result.confidence), result.status)

Everywhere else in the assembly code (__init__.py's _output_column and _build_projection) calls the plain resolve(ref, name) directly, because by that point the alias has already been resolved once while the relation graph was built — OutputCol.inputs stores an InputRef(column, alias) pair, and _resolve_inputs (lineage.py:186) is what re-binds that alias via bind_alias before recursing.

04 _resolve: the four cases

Given a relation and a column name, exactly one of four things happens:

# lineage.py:157-184, abridged
def _resolve(self, ref: RelationRef, column: str) -> Resolution:
    info = self.graph.get(ref)
    if info is None or info.is_table:
        return Resolution([ColumnNode(relation=ref, column=column)], "explicit")  # 1. terminal

    output = info.outputs_by_name.get(column.lower())
    if output is not None:
        if output.kind == "derived":
            return Resolution([ColumnNode(relation=ref, column=output.name)], "explicit")  # 2. derived, stop here
        return self._resolve_inputs(info, output.inputs)  # 2b. passthrough, follow the input

    if info.is_setop:
        return self._resolve_branches(info, column)  # 3. ask every branch by name

    if info.star_sources:
        target, confidence = self._pick_star_source(info, column)
        ...  # 4. no explicit column, but a * covers it

    return UNRESOLVED

Case order matters: an explicit column (case 2) always wins over a star (case 4), even if the relation also has a * in its SELECT list — that's exactly what happens with dedupped in person.sql, whose SELECT is *, row_number() ... as rn: rn hits case 2 (derived, stops), everything else falls through to case 4 (the single star source, person).

05 bind_alias: which relation owns a name

Before a column can be resolved, its alias (if any) has to be mapped to a concrete relation. bind_alias is a priority list, first match wins:

  1. Qualified, alias found in this scope's bindings → that relation, explicit.
  2. Qualified, alias not local → walk up info.parent looking for a correlated outer binding (_bind_outer, lineage.py:294). Still explicit if found.
  3. Qualified, alias nowhere → record an unknown_alias ambiguity, drop it.
  4. Unqualified, exactly one binding declares it explicitly → that relation.
  5. Unqualified, >1 binding declares it → unqualified_multi_source ambiguity, dropped — genuinely ambiguous, no guessing here.
  6. Unqualified, only one binding total → that binding, trivially.
  7. Unqualified, nobody declares it, but there's a * → falls through to star-over-join (§6).
  8. No bindings at all → try a correlated outer unqualified match, else unresolved_column.

Step 5 is worth dwelling on: it's stricter than the star case. If two explicit, named columns collide, that's a real authoring ambiguity in the SQL and the Resolver refuses to guess. Guessing is reserved entirely for *, where sqlrunner has decided a best-effort attribution is more useful than refusing outright.

06 Star over join

When a relation does select * (or forwards to one) over more than one FROM/JOIN source, and the requested column isn't explicitly declared anywhere, _guess_star_source (lineage.py:376–393) tries three rules in order. Each was run for real below.

Rule 1 · declaration

A candidate explicitly declares the column

Only fires when a candidate is itself a CTE/subquery with a named output — raw tables never "declare" anything to the graph, so this rule is dead on joins of two plain tables.

Rule 2 · qualification

The column is qualified elsewhere in the same scope

A join condition like on o.id = oi.order_id counts — it lives in the same scope as the star, so it silently proves id belongs to o before you even reach the SELECT list.

Rule 3 · no evidence

Leftmost candidate wins, confidence downgrades to guessed

FROM-clause order decides. This is the only rule that star_over_join_behavior="error" treats as fatal — rules 1 and 2 are evidence, not guesswork, so error mode lets them stand.

Rule 1, traced

Rule 3, traced — and why id was the wrong column to test it with

First attempt used select id from combined against the same orders o join order_items oi on o.id = oi.order_id. That still resolved to inferred, not guessed — because o.id in the join's ON clause is a qualification in the same scope, so rule 2 claims it first. Getting a genuine zero-evidence case meant picking a column that appears nowhere else in the query at all.

07 Memoization & cycles

resolve() is the public, memoized wrapper; _resolve() is the raw recursive step it caches (lineage.py:137–153).

# lineage.py:137-153
def resolve(self, ref: RelationRef, column: str) -> Resolution:
    key = (ref, column.lower())
    cached = self._memo.get(key)
    if cached is not None:
        return cached
    if key in self._active:
        return UNRESOLVED  # recursive CTE / unwindable cycle

    self._active.add(key)
    try:
        result = self._resolve(ref, column)
    finally:
        self._active.discard(key)

    self._memo[key] = result
    return result

Two safety nets here: a memo cache keyed on (relation, lowercased column) so a fanned-out chain (e.g. eight columns in projected all touching dedupped) never re-walks the same subgraph twice, and an active set that turns a recursive cycle (a CTE that references itself) into a clean UNRESOLVED instead of infinite recursion.

Traced live below: resolving name straight from cte:dedupped re-triggers the star-over-join pick (that part isn't memoized independently — _pick_star_source has its own _star_memo), but the underlying table:person.name hit is fresh here since it wasn't resolved earlier in the run.

09 Takeaways

  • Direction is the whole design. Resolving backward from a reference to its source sidesteps ever needing a real schema catalog.
  • Confidence is a floor, not a score. weakest() means one guessed hop anywhere in a chain caps the whole chain at guessed — it only ever goes down.
  • Guessing is scoped tightly. Named-column collisions (bind_alias step 5) are never guessed, only reported as ambiguous and dropped. Only an unresolvable * over a join falls back to leftmost-wins.
  • Join conditions are evidence. on o.id = oi.order_id silently resolves what looks like it should need a guess — this is rule 2, and it's easy to underestimate how often it fires in real SQL.
  • Memoization is per-(relation, column), not global — safe for diamond-shaped graphs, and the active-set guard makes self-referencing CTEs degrade to UNRESOLVED instead of a stack overflow.
